# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A static, backend-free browser DAW (React 19 + TypeScript + Vite + Tone.js + Zustand + SCSS) for a five-member fan-made "K-ON!" band. Deployed to GitHub Pages. Instruments are CC0 recordings (Karoryfer / Versilian, built by `scripts/build-sample-packs.ts`, credited in `public/instruments/CREDITS.md`) with in-browser synth fallbacks; the repo must not ship official character artwork (or anything traced from or modelled on it), official recordings or scores. The only character art allowed is the project's own tiny pixel figures (`pixelMembers.ts`, below), at the owner's request. Any sample pack added must be redistributable (record its `license` in `SAMPLE_PACKS`, `src/audio/audioConfig.ts`, and in CREDITS.md).

## Commands

Package manager is **pnpm 9** (`corepack enable`).

```bash
pnpm dev                 # dev server, http://localhost:5173
pnpm build               # tsc -b + vite build → dist/
pnpm typecheck           # tsc -b only
pnpm lint                # eslint .
pnpm test                # vitest run (jsdom, fake-indexeddb)
pnpm test:watch
pnpm vitest run src/lib/time.test.ts          # single file
pnpm vitest run -t "<test name>"              # single test by name
pnpm format              # prettier (printWidth 100, double quotes, trailing commas)
pnpm demo:midi           # regenerate public/demo/after-school-jam.mid from src/features/band/demoSong.ts
FFMPEG=/path/to/ffmpeg pnpm samples:build   # rebuild public/instruments/* + samplePacks.generated.ts from CC0 sources
```

CI (`.github/workflows/deploy.yml`) runs lint → test → build on push to `main`, with `BASE_PATH=/<repo-name>/`. Asset URLs must go through `import.meta.env.BASE_URL` (see `samplePackUrl`) so they work under that sub-path.

TS is strict with `noUncheckedIndexedAccess`, `noUnusedLocals/Parameters` and `verbatimModuleSyntax` (use `import type`). Import via the `@/` alias for `src/`.

## Architecture

**React owns state and UI; `AudioEngine` owns sound and time.** Components never import Tone.js.

- `src/audio/AudioEngine.ts` exports a singleton `audioEngine`. `start()` must be called from a user gesture (`ensureAudio()` in `src/hooks/useAudioEngine.ts`). Before start, `sync()` only remembers the last project and replays it once started.
- `useAudioEngineBridge` (mounted once) subscribes to `useProjectStore` and calls `audioEngine.sync(project)` whenever the `project` reference changes. `sync` is a diff: `AudioTrack.setNotes` is a no-op when given the **same notes array reference**, so store updates must keep untouched arrays referentially identical and must create new objects (immutable updates) for things that changed. Engine events (instrument load state, transport end, errors) flow back into `useStudioStore`.
- Two Zustand stores:
  - `useProjectStore`: the persisted `StudioProject` (song, tracks, mix). Always exactly five tracks, one per `MEMBERS` entry in `src/features/band/members.ts`, keyed by `memberId`.
  - `useStudioStore`: ephemeral UI/runtime state (transport status, audio-started, instrument load states, pending MIDI import, notices) plus `settings` (persisted to localStorage).
- `PersistenceProvider` hydrates settings (localStorage) and the project (IndexedDB, key `"current"`), then debounce-saves the project (400 ms), flushing a pending save on `pagehide` / hidden. It subscribes before the IndexedDB load, and a project changed meanwhile (an import, a fader) wins over the stored one; when storage is "unavailable" it doesn't try to save. Audio objects are never stored. Loaded projects go through `validateProject` (`src/services/storage/projectValidation.ts`), which repairs fields and drops bad notes, but returns `null` (fall back to the demo) on wrong `version` or a missing member track. **If you change `StudioProject`'s shape, bump `PROJECT_VERSION` in `src/types/project.ts` and update the validator.** Original MIDI files are stored as Blobs in a separate IndexedDB store, referenced by `midiBlobKey`; `pruneMidiBlobs` deletes every other one after an import and on startup (they were up to 5 MB each and piled up). The validator requires finite numbers (IndexedDB keeps Infinity and NaN) and integer pitches, folds `baseBpm` into range and never lets `durationSeconds` end before the notes.
- The playhead and position readout use `usePlaybackPosition` (requestAnimationFrame polling `audioEngine.getPosition()`) and write to the DOM/canvas directly. Playback must not cause React re-renders; don't put position into a store.

### Time model (`src/lib/time.ts`)

Notes are stored in **song seconds** (seconds at the song's own tempo map, resolved by `@tonejs/midi`). The engine converts them to Transport ticks against `project.baseBpm` at `PPQ = 192`; note durations are also scheduled in ticks. The user's playback tempo (`project.bpm`) only changes `Transport.bpm`, so tick positions, playhead and audio never drift. All positions crossing the engine API (`seek`, `getPosition`) are in song seconds. `durationSeconds` is rounded up to a whole bar (`songLength`) so loops land on the downbeat. A bar is counted in quarter notes everywhere (`quarterBeatsPerBar`: 6/8 → 3, 2/2 → 4). Tempos keep two decimals (`clampBpm`, 40–300): rounding an imported 133.33 BPM to 133 made songs drift against synced footage. A song's *base* tempo outside 40–300 is folded by octaves (`foldBpm`: 400 → 200), never clamped: it only sets the grid, and clamping it made the song play at the wrong speed. Song end is detected by a Transport-scheduled event plus `setTimeout` (not `Tone.Draw`, which is dropped in background tabs).

### Audio track details

Each `AudioTrack` has two voices: a sequenced voice behind a `Tone.Channel` (volume + mute/solo) and a separate **live** voice for keyboard playing that ignores mute/solo and transport stops. **Scheduling rule:** in a Part / Transport callback, clamp a note's start to the audio clock (`notBefore` in AudioTrack: `Tone.getContext().currentTime`), never to `Tone.now()`. `Tone.now()` is the clock plus the look-ahead, which is exactly where the callback's scheduling window ends, so clamping to it pushes every note to the end of its 50 ms window: notes land up to 50 ms late and the ones in one window fire together (measured: hi-hat eighths at 150 BPM were 11 ms off on median, 56 ms worst; after the fix 0). Live playing uses `Tone.immediate()` for the same reason (`Tone.now()` adds 0.1 s of latency). `AudioEngine.start()` shares one in-flight start, so calls during it (a first strum calls it per string) never build a second audio graph; `AudioTrack.setInstrument` counts its calls (`voiceRequest`) so only the latest builds voices. Each track's channel is panned to its member's place on stage (`BandMember.pan`: Yui left, Azusa right, Mugi a little right, Mio and Ritsu near the middle); the vocal has its own centred channel. Every channel sends to one shared room (`ROOM_BUS`, a reverb return in `AudioEngine`) and all tracks meet on a bus with a gentle glue compressor before the master; the voices' own reverbs are kept small. Mute/solo rules live in `src/lib/mix.ts` (mute always wins; with any solo, only soloed tracks play). Going inaudible, pausing, stopping or seeking calls `releaseAll()` to cut ringing notes. **Tone's `Sampler.triggerAttackRelease` forgets a note as soon as its release is scheduled, so `Sampler.releaseAll()` can't cut sequenced notes**: every Sampler-based voice plays sequenced notes through `SampledNotes` (voices.ts), which keeps each source until it ends and stops them on a cut. `MelodicVoice` schedules PolySynth releases itself with a generation counter, so a release left from before a seek can't cut the same note played again. The fader and mute/solo meet in `AudioTrack.setMix`: Tone's `mute` is just the volume at -Infinity, so setting them separately un-muted a muted track on the next fader move.

Synth voices in `voices.ts` are modelled on each member's known gear (comment above `createSynthVoice`): the guitars, the bass's finger pluck and Mugi's FM piano are **rendered once in plain JS** (`karplus.ts`, `fmPiano.ts`; which notes per `RENDERED_SETS`; done in `SampleManager.loadSynth`, yielding between notes and reporting progress) and played by a `Tone.Sampler`; the guitars go through `guitarAmp()`; bass and keys are `LayeredVoice`s, and the keys' string pad is a single-saw PolySynth wrapped in `HeldNotesOnly` (sequenced notes ≥ 0.3 s only, max 32 voices). **CPU budget rule:** the audio thread overloads (output drops out or goes silent) when dense parts run many live synth voices. Tone's `PluckSynth` (an AudioWorklet per string, running even when silent) and a 64-voice FM PolySynth both did this; prefer rendered samples for anything that can sound many notes at once, and keep live PolySynths small (`MelodicVoice` caps at 48 by default). To check, play a dense MIDI file in headless Chrome and compare `AudioContext.currentTime` against wall time: below ~1.0 means the audio thread can't keep up. `SYNTH_TRIM_DB` was set by rendering a phrase per instrument with `Tone.Offline` and matching RMS, so re-measure after changing a patch rather than guessing.

**Feel** (`src/lib/feel.ts`, pure): sequenced notes get each member's timing push, jitter, dynamics, downbeat accent and chord strum. The band locks to Ritsu: pushes are within 2 ms of each other and jitter is a few ms at most (bigger, per-member offsets made fast songs sound like five people playing separately), and `capStrums` keeps a strum within a third of a sixteenth (`humanize`, `strumOffsets`: down-strums low→high, off-beat eighths up-strum). `AudioTrack` knows its member and applies it in the Part callback; drums never strum, live notes are untouched. `settings.feel` (`"character"` | `"steady"`, toolbar ✨ toggle) reaches the engine through `audioEngine.setFeel` in the bridge; `"steady"` removes timing and dynamics but keeps the strum roll.

`SampleManager` loads instruments lazily and shares buffers across tracks. All five instruments have a recorded pack in `SAMPLE_PACKS` (files from the generated `samplePacks.generated.ts`; don't hand-edit it, rerun `FFMPEG=… pnpm samples:build`, which needs an ffmpeg that reads FLAC and writes MP3). Pack voices come from `createPackVoice` (same member voicing as the synths: guitar amps, bass compression, `SampledDrumKit`; the piano is `VelocityLayers` over the pack's `soft` and main recordings, **no string pad**: a sawtooth pad droned audibly under long held notes of real piano). `load()` never rejects: if a pack fails, the synth voice is prepared instead and the state is `"error"` so the mixer shows Retry. Only Retry (`load(instrument, true)`) fetches a failed pack again; style and patch changes rebuild voices without it (`AudioEngine.rebuildInstrument`). Files of a failed pack still arriving don't report progress (that put the state back to "loading" for good, disabling Play). Keys on a synth patch don't load the piano pack at all. Notes stay silent until an instrument's voice exists. Instrument IDs: `lead-guitar`, `rhythm-guitar`, `bass`, `drums`, `keys`. Drum samples are keyed by GM note name (`C2` = kick 36, `D2` = snare 38); the kit has one sample per piece and `drumSampleNote()` routes every other GM drum note to the closest piece. Pack `volume`s were set the same way as `SYNTH_TRIM_DB` (offline render, matched RMS).

**Which recording is whose** (members' real gear → closest CC0 recording, see the build script): Yui's Les Paul → Epiphone humbucker guitar (emilyguitar); Azusa's Mustang → Hofner (no free Fender single-coil exists; her amp is voiced brighter instead); Mio's Jazz Bass → Squier Jazz Bass (growlybass); Ritsu's Hipgig → Big Rusty Drums with kick +5 / toms +3 semitones (`retune` in the build: smaller shells); Mugi's Triton → recorded piano plus synthesized patches. **Sample libraries disagree on octave names: never trust a file name or an SFZ `pitch_keycenter` for the sounding pitch. Measure it** (autocorrelation on the decoded file, taking the shortest lag within 85% of the best so harmonics can't fake an octave). The bass libraries name files an octave above what they sound ("e2" is the 41 Hz open E, MIDI 28), and the bass shipped before this check was an octave low. The guitar libraries differ from each other (Black And Green "f3" = MIDI 41, Emily "e2" = MIDI 40), and the piano names an octave below ("C0" = MIDI 24).

**Playing style** (`src/lib/playStyle.ts`, pure; `settings.playStyle`: original / rock / punk / ballad / swing; picker in `TimelineToolbar`): `AudioTrack.schedule()` turns the written notes into ticks, runs `arrange(style, instrument, ...)` (power chords, eighth chugs, phrase crashes, legato, arpeggios, a swing time warp), then the strums and the feel. It depends on the track's *instrument*, so changing instrument or style re-schedules the Part (works mid-song). The timeline always draws the written notes. The guitar amps also change per style (`STYLE_AMPS` in voices.ts, via `SampleManager.style`; `AudioEngine.setStyle` rebuilds both guitar tracks). Each style's `levelDb` was measured (offline render, matched to the "original" RMS): re-measure after changing an amp. `strumOffsets` also treats the swung off-beat (2/3 of a beat) as an up-strum. **Auto drums** (`settings.autoDrums`, 🥁 toolbar toggle, only enabled for rock / punk): a drums track with no written notes plays `drumGroove` in every bar where another part sounds. With the solo round on, only the notes before the round count (`BandContext.songEndTicks`, from `PlayedSong.songEnd` passed to `sync`): Ritsu's solo after the song made a drumless song look drummed, and it lost its groove. `AudioEngine.bandContext` computes those bars (`playedBars`) and memoises the `BandContext` object by the non-drum notes-array references, so `AudioTrack.setBand` only re-schedules when something really changed (sync runs on every volume drag). The timeline still shows Ritsu's lane empty.

**Vocals** (`src/features/band/vocals.ts`): Yui sings lead and Mio harmony. A singer's part is `StudioTrack.vocal` (optional, so older saved projects still validate without a version bump; the validator keeps it only for singers). `AudioTrack.setVocal` gives it a second Part and a `VocalVoice` (voices.ts: rendered sung notes played by a Sampler: `singer.ts` renders each note once in plain JS (a Rosenberg glottal pulse with a high open quotient, breath noise pulsed by the glottal cycle, five cascaded formant resonators at teenage-girl values (above adult female), a low cut (`lowCut`, ~250 Hz) taking off the chesty weight that makes a synthetic voice sound grown-up or male, vibrato that grows in after the onset, slow pitch drift, shimmer and a scoop), every 2 semitones per singer (`SUNG_RANGES` in voices.ts, cached per page; until rendered the part is silent). `YUI_VOICE` is a bright, light "ah", `MIO_VOICE` a warmer, rounder "oh". Before the first note and after every rest of at least 0.35 s, the singer breathes in (`breathTimes`: 0.32 s ahead, never over the last note; `renderBreath`, a band-passed noise rush at `BREATH_DB`, scheduled as `breath` events in the vocal Part). `fitToVoice` moves a whole part by octaves so it sits in a girl's range (lead around B4, harmony around F#4). No CC0 recording of a sung female vowel was found (VCSL has no vocals; sfzinstruments' legato_vocal_tutorial is Karoryfer's Hadzi-Fia, a male voice), which is why the voice is synthesized. These are character types: never model a real voice actor) on the **same channel**, so the member's volume, mute and solo apply. Vocals go through `arrangeVocal` (never chugged, power-chorded or drummed) and the member's feel. **What plays a vocal part** is `settings.vocalSounds` (per role: `voice` | `guitar` | `synth` | `piano` | `strings`; picker "Lead vocal on" / "Harmony on" in the live panel when Yui or Mio is selected): `createSinger` in `audio/vocalSounds.ts` builds the singer or an `InstrumentSinger` (Yui's lead-guitar pack through her amp in the current style, rebuilt on a style change; Mugi's recorded piano via `SampleManager.createVoice("keys", "piano")`, which overrides her chosen patch; or her Triton synth lead / strings), raised by `VOCAL_SOUND_GAIN_DB` (measured: every sound within ~0.6 dB of the lead vocal, harmony 3 dB under). Instruments don't breathe. `AudioTrack.buildVocalVoice` counts requests so only the latest build is kept. `settings.vocals` holds one switch per role (🎤 on the mixer strip, disabled when the song has no vocal part), and reaches the engine through `setVocals`. On import, `suggestMapping` gives tracks whose names say they are sung (`isVocalName`: vocal, voice, choir, women and men, ボーカル, 歌, 主唱, 和声 …) to Yui (lead-sounding first) and then to Mio (backing / harmony / chorus), marked `vocal: true` in the `TrackAssignment`. The dialog offers "Yui (lead vocal)" and "Mio (harmony vocal)" as `yui:vocal` / `mio:vocal`. The timeline draws a vocal as outlined notes one note-height above the member's own notes (a singer often doubles their instrument's tune). Levels are in `VOCAL_TRIM_DB`, measured like the other trims. The voice is wordless, and must never imitate a real singer.

**Solo round** (`src/lib/soloRound.ts` + `src/lib/scoreAnalysis.ts`, pure; `settings.soloRound`, ⭐ toolbar toggle): after the song, Ritsu, Mio, Tsumugi, Azusa, then Yui each play a 4-bar solo, then one final chord together. **The solos come from the song:** `barChords` names each bar's chord (non-drum pitch classes weighted by length, the bass doubled, matched to the 24 triads), `commonProgression` picks the 4 bars of chords the song repeats most (with the key known, progressions with chromatic passing chords score 0.3: Fuwa Fuwa Time's B–C–C#m climb would otherwise win), and each member develops their **own part's most played bar** (`signatureFigure`: bars compared by top-line rhythm and intervals, at least 3 different pitches, 2 for bass, scored by count × pitch variety; `signatureGroove` for drums): Ritsu her groove, then with ghost notes, its kicks under a tom run, a fill; Mio her groove on the solo chords, octave pops, a walk up; Mugi her phrase in thirds, an arpeggio, a run; Azusa her line, then scale runs between its notes, a climb; Yui her hook, a step up, twice as fast, a long high note. `placeFigure` moves a figure onto each chord (first note to the nearest chord tone, shape kept, snapped to the key). A member with no part uses the song's tune (a vocal, else Yui's part); with no material at all, the `generic…` solo for the instrument. Quiet backing from Ritsu and Mio (none under the drum solo). Key by `detectKey` (Krumhansl). Never saved: `stores/playedSong.ts` (`usePlayedSong` / `getPlayedSong`) gives the engine bridge, `Timeline`, the transport readout and the recording the song *as played* (the round appended, a longer `durationSeconds`, `spots` that light each soloist's lane with a SOLO tag), memoised by what changes the music, keeping note-array identity so a volume drag doesn't re-schedule every part. Seeded by the song name.

**Count-in and metronome** (`settings.countIn` / `settings.metronome`, switches beside the BPM field): `Metronome.ts` clicks on a `scheduleRepeat` every `PPQ` ticks, accenting beat 1. Its output goes to `Tone.Destination`, **not** the master, so clicks are never in video recordings. A count-in schedules one bar of clicks on the audio clock and starts the Transport at a future time (`TransportController.play(at)`); while waiting, `status` reports "playing". A Tone pause before a scheduled start is ignored (the start still happens), so `pause()` during a count-in stops and puts the ticks back, and the engine disposes the count-in synth to silence the clicks still to come.

**Mugi's sound** (`settings.keysPatch`: piano / strings / synth / organ, `src/audio/keysPatches.ts`, picker in the live panel): `SampleManager.keysPatch` makes `createVoice("keys")` return `createKeysPatchVoice` for the synth patches, and `AudioEngine.setKeysPatch` rebuilds every keys track (the bridge sets it before the first sync). Each patch is one capped PolySynth (strings and organ 40 voices, single oscillator; synth 24), trimmed by `KEYS_PATCH_TRIM_DB`; `MelodicVoice` skips a note quietly when its PolySynth is full, because Tone's per-note "Max polyphony exceeded" warning floods the console in dense parts. Stress-test any new patch with a dense MIDI file (audio clock / wall clock must stay ≈ 1.0).

### MIDI import flow

The picker's `accept` comes from `songFileAccept()`: none on phones and iPads, because iOS greys out .gp5 / .mxl files (it only allows types it knows, whatever `accept` lists); computers keep the filter. `useMidiImport.openFile` → `readSongFile` (file checks; `songFormat()` says "midi" or "score") → for scores (Guitar Pro 3–8, MusicXML), `scoreToMidi` (alphaTab `ScoreLoader` + `MidiFileGenerator`, **dynamically imported**: it's a 1.2 MB chunk that must stay out of page load; its console logging is switched off via `alphaTab.Logger.logLevel`) gives MIDI bytes (one MIDI track per part, named in UTF-8 by `nameMidiTracks`, behind an empty first track) and the title → `parseMidi` (`@tonejs/midi` → `NoteEvent`s) → `suggestMapping` (sung parts to the singers first; then a track **named after a member** (`memberFromName`: Yui / Hirasawa / 唯, Azusa / Nakano / 梓, nicknames like Azu-nyan count less; a one-kanji given name only counts on its own, not inside a word: 律 is in 主旋律, 唯 in 唯美; a named track only stops unnamed drums / bass going to Ritsu / Mio when it is itself drums / bass; fan transcriptions label parts "Guitar: Yui Hirasawa") goes to that member, one per member; then unnamed drums → Ritsu and bass → Mio; then the rest busiest first, each to a member who plays that instrument, and only after that to anyone free, so a keys part is never left out because a spare guitar took Mugi; `familyOf`: a clear track name, via `familyFromName` in en/ja/zh, wins over the GM program, because converted MusicXML usually comes out as program 0; "rhythm" guitars prefer Azusa; drums→ritsu, bass→mio, guitar/keys/lead → yui/azusa/tsumugi) → stored as `pendingImport` (the MIDI bytes, and the score title if any) for the user to edit. Converted files (Songsterr's GP5 converter) break assumptions real Guitar Pro keeps, so `scoreToMidi` repairs the score: `padVoices` (bars stored with a zero-beat second voice crash alphaTab when it links bars) and `assignChannels` (every part pointed at one channel, even above 15, which alphaTab turns into one shared playback object: copy it per part, give each part its own channel, drums on 9, and clear the shared guessed instrument and its first-bar instrument changes). `parseMidi` decodes track names as UTF-8 (`decodeMidiText`) and puts back together what @tonejs/midi split apart at program changes (`partsOf`): a piece with controllers but no notes hands its name to the notes after it, and an unnamed piece on the same channel right after a part (an instrument change mid-song) is joined onto it. Names are decoded *before* trimming: `trim()` on the raw one-char-per-byte text cuts a 0xA0 byte (the end of ム in ドラム). `nameMidiTracks` also writes each part's program change first, so a score part is never split and keeps its instrument even when it shares a channel past 15 parts. Tests build Guitar Pro files with alphaTab's own `Gp7Exporter` from a MusicXML fixture (`src/test/scores.ts`); jsdom lacks `Blob.arrayBuffer`, polyfilled in `src/test/setup.ts`. `confirm` → `buildTracksFromMapping` (merges tracks assigned to the same member; members with nothing assigned get an empty part, only their volume / mute / solo carry over) → saves the MIDI blob → `engine.stop()` → `projectStore.loadSong`. The timeline grid uses only the first time signature.

### UI language (en / zh)

All user-visible text lives in `src/i18n/strings.ts`: an `en` object whose type (`Strings`) the `zh` object must satisfy, so a missing translation is a type error (`strings.test.ts` also checks key parity). Components call `useT()`; code outside React (store callbacks, async handlers, notices) calls `getT()`. The language is `settings.language`, persisted with the other settings and defaulted by `detectLanguage()`. Member display names and roles come from `t.memberName` / `t.memberRole`, not from `MEMBERS`. Errors thrown by the MIDI file and parse layers carry a `code` plus `fileName` and are translated where they are shown (`useMidiImport`), so keep their English `message` only for logs and tests. Tests render in English (jsdom reports `en-US`).

### Responsive layout

One breakpoint, `$narrow: 760px` in `studio.scss`, mirrored by `NARROW_QUERY` in `useMediaQuery.ts` for JS (one-octave keyboard, lane labels drawn on the timeline canvas). `TOUCH_QUERY` (no hover, coarse pointer) swaps keyboard hints for tap hints and enlarges controls in CSS. On narrow screens the transport bar is `position: sticky` and `useHideOnScroll` slides it away while scrolling down (the pure rule is `scrollVisibility`).

### Live instrument panel

`liveLayoutFor(instrument)` in `src/lib/fretboard.ts` picks the on-screen instrument: `fretboard` (lead guitar, bass, with tunings in the same file), `chords` (rhythm guitar strum pads, `CHORDS`), `piano` (keys) or `drums` (kit laid out by `DrumPad.area` grid areas). All of them feed `useKeyboardInput`, which tracks every sounding note by *source* (`key:<KeyboardEvent.code>`, `ptr:<id>`; the code, not the character, or Shift turned ";" into ":" between keydown and keyup and the note stuck; Meta releases everything, since a Mac sends no keyup for keys let go while Cmd is held). A strum is one source with a sub-source per string (`src|0`, `src|1`, ...), started `STRUM_MS` apart; `release(src)` stops the whole group and cancels strings that haven't started yet. On the fretboard the octave control only moves the computer-keyboard notes, so it is hidden on touch screens. A member with `leftHanded` in `MEMBERS` (Mio) gets `Fretboard leftHanded`: the grid runs `direction: rtl`, fret wires and the nut swap sides, and the fret-window arrows swap so they still point the way the frets go.

### Look and the score drawing

**Member badges** (`MemberBadge`: mixer, member picker, live panel) show the member's instrument as pixel art drawn for this project (`features/band/pixelInstruments.ts`: 16 × 16 cell sprites in the member's colour; guitar strum, bass pluck, snare stick down, cymbal tilted on a crash, keys held down; Mio's guitar or bass mirrored). `poseAt` reads the pose from the member's notes; a badge runs its own animation frame loop only while the transport plays (so tests that mock the engine never touch `getPosition`) and repaints only when `poseKey` changes. The recording frame draws the same sprites, on a light tile of the member's colour so the ink outline shows on dark: beside each lane name in the scrolling view (`LaneInput.instrument` / `leftHanded`, showcase only) and under the hit line in the falling-notes view. ### Offline / installable (PWA)

`index.html` links `public/manifest.webmanifest` and the icons in `public/icons/` (rendered from the favicon artwork; the maskable and Apple icons are full-bleed). The service worker is **generated at build time**: the `serviceWorker()` Vite plugin (`scripts/serviceWorker.ts`) fills `scripts/sw-template.js` with the app-shell file list and two versions (shell per build; samples hashed from `public/instruments` names and sizes), and writes `dist/sw.js`. Lazy chunks (the score importer) aren't precached; they are cached on first use. Pages are network-first, so a deploy shows on the next visit. Cache lookups use `ignoreVary`, because module scripts are CORS requests and a `Vary: Origin` header made them miss offline. `registerServiceWorker()` only runs in production; once the worker controls the page (not on a hard reload) it fetches every sample at idle time, through the worker, but only when `shouldWarmSamples` says the connection is fast and unmetered, or, when the browser reports nothing (Safari, Firefox), on a computer (not `TOUCH_QUERY`): phones fetch each instrument on its first Play. Versions hash file *contents* (a re-rendered sample has the same size). Install and page fetches bypass the HTTP cache (`cache: "reload"` / `"no-cache"`); only `text/html` navigations become the offline page; older builds' runtime caches (lazy chunks) are kept for a week from the deploy that retired them (a `/__retired__` entry in the cache records when) so a tab open across a deploy can still import scores; samples missing from the cache are fetched with `no-cache` (their names don't change when re-rendered); a page that hasn't answered in 4 s is served from the cache; the fonts cache only keeps successful CORS responses (the stylesheet link has `crossorigin`), at most 80. To check: `BASE_PATH=/k-on-band-studio/ pnpm build`, then `pnpm vite preview`, let the caches fill, kill the server, reload and play. In Git Bash, prefix `MSYS_NO_PATHCONV=1` or it rewrites BASE_PATH into a Windows path.
